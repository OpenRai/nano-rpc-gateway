Gateway JSON-RPC 2.0 API and SSE

JSON-RPC 2.0 for Nano ledger queries

Send JSON-RPC 2.0 requests to this gateway. It translates ledger calls into actions on Nano node's separate custom JSON RPC interface. Use SSE to receive confirmation events.

Gateway JSON-RPC 2.0 methods

Send these methods in JSON-RPC 2.0 requests to POST /rpc. For ledger methods, the gateway sends the corresponding action to the Nano node's custom JSON RPC interface. The gateway's rpc.discover method returns its OpenRPC document. Examples show JSON-RPC 2.0 requests and result shapes.

Account confirmation stream

Open GET /events/confirmations, or POST it with the subscribe options as a JSON body, and filter by accounts. Each SSE record contains a JSON-RPC notification.

Account tracking

Watch accounts and update local state

Use this sequence to track a send or receive from submission to cementing. The stream reports cemented blocks only. It does not report votes or election progress.

Notification types

  • nano.confirmation identifies a matching cemented block.
  • When the stream closes, the upstream node WebSocket went away. Reconcile before applying later events.
  • Use params.hash as the idempotency key. Store it and ignore duplicates; the node can send the same confirmation more than once.
  • params.subtype inside params.block identifies a state send or receive.
  • params.time is the event time in milliseconds since the epoch.

Stream limits

  • The stream does not emit aggregate balances, derived balance events, votes, or telemetry.
  • A client must handle a confirmation that was not delivered.
  • Balance responses use receivable, not a pending field.

Track a recipient before sending

  1. Open GET /events/confirmations?accounts=<account>[,<account>], or POST /events/confirmations with the same options as a JSON body when the filter outgrows the request line. Keep the connection open.
  2. After the stream opens, call accounts_balances once with the watched accounts and include_only_confirmed: true. Store each result.balances[account] value.
  3. Submit the block with process. Persist result.hash as the submitted block hash.
  4. When nano.confirmation.params.hash equals that hash, mark the submission cemented. A recipient filter matches an incoming state send through params.block.link_as_account.
  5. After each matching confirmation, call accounts_balances once for the complete watched set. Publish each returned balance and receivable value. This is event-triggered batch refresh, not polling.
  6. There is no replay and no cursor. If the stream closes, or you change the tracked set, open a new stream and reconcile.

Read the batch balance result

PathTypeMeaning
result.balancesobjectOne entry for each requested account. It is not a total.
result.balances[account].balancestringCemented account balance in RAW.
result.balances[account].receivablestringCemented incoming sends not yet received, in RAW.
result.errors[account]string, optionalNative per-account validation error.

params.block.balance is the balance of params.account after that block. For a send addressed to a watched recipient, it is the sender balance. Use accounts_balances for the full balance and receivable state of the recipient.

Handle a missing notification or reset

  1. When a submitted hash has no confirmation after about 5 seconds, call block_info with that hash.
  2. Read result.confirmed. A value of true means the block is cemented.
  3. When the stream closes, reconcile every tracked account with accounts_frontiers and account_history before applying new confirmations. The gateway cannot resume a stream.
  4. Use block_info for each submitted hash whose terminal state remains unknown.

Check the current account frontier

Use this sequence when you have an account but no submitted block hash. It checks whether the current frontier for that account is cemented.

  1. Call account_info for the account.
  2. An account the node does not know returns the node's own error rather than a result; there is no opened flag to read.
  3. Read result.frontier. This is the current frontier and can be ahead of cemented state.
  4. Call block_info with that hash. Read result.confirmed.
  5. Request include_confirmed to receive result.confirmed_frontier and result.confirmed_balance; without it the response carries no confirmed_* fields.

Detect every change with a frontier delta

The canonical refresh. Three batch calls plus one account_history per changed account, whatever the size of the account set.

  1. accounts_frontiers with accounts: compare each result against the stored frontier hash.
  2. account_history with head set to the stored hash, reverse true and raw true, for each changed account. head is inclusive, so the first entry is the head block itself: dedupe by hash rather than dropping entry 0. raw is required because the summary form skips change and epoch blocks.
  3. accounts_receivable with source, for incoming blocks that are not yet received.
  4. blocks_info with the new frontier hashes, and read confirmed. If false, escalate with block_confirm.

accounts_receivable also reports an incoming send that has not been received yet, with source to name the sender. block_confirm asks online representatives to confirm a block; its result reports that no error occurred and never that the block confirmed.

The fallback delay and frontier sequence follow the Nano confirmation-tracking guidance. The gateway exposes the methods linked above.
